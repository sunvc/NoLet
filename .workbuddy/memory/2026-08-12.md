## 修复 ScriptPreview 滚动条与顶部不对齐 (ScriptPreview.swift)

- 现象：ScriptPreview 代码页加载后，右侧滚动条 thumb 停在中部，未与文本顶部（导航栏下）对齐。
- 根因：`applyContentInset()` 修改 `textView.contentInset.top`（导航栏高度）后，iOS 会自动调整 contentOffset 保持可视内容不动（contentOffset.y 停在 0 而非 -topInset），scroll indicator 因此显示在中轨位置。原有 `pinToTop()` 只在 textView.layoutSubviews 中调用，时机不足。
- 修复：
  1. `EditorContainer.applyContentInset()` 末尾追加 `textView.pinToTop()`（inset 变化后立即同步 offset）
  2. `EditorContainer.layoutSubviews()` 在 `super.layoutSubviews()` 之后追加 `textView.pinToTop()`（子视图布局完成、bounds 有效后兜底）
  - `pinToTop()` 有 `!userHasScrolled` 保护，用户手动滚动后不受影响；调用幂等。
- 验证：`swiftc -parse` 通过。全量 xcodebuild 因沙箱阻止 SPM sandbox-exec 无法在命令行验证，需在 Xcode 中构建。
- 经验：UITextView 自定义 contentInsetAdjustmentBehavior=.never + 手动 topInset 时，contentInset 变化后必须同步 pin contentOffset，否则滚动条指示器与内容顶部错位。

## 为 ScriptPreview 编辑器添加 JS 语法高亮 (ScriptPreview.swift)

- 需求：代码编辑器（LineNumberedTextEditor，UITextView）支持 JS 语法高亮。确认 ScriptManager 只处理 .js 文件。
- 方案选择：用户选「原生正则高亮」(零依赖) 而非 Highlightr 第三方库。
- 实现：在 ScriptPreview.swift 末尾新增 `JSSyntaxHighlighter` 单例类：
  - 用 NSRegularExpression 匹配：块注释/行注释、字符串(单/双/模板)、数字(含0x)、关键字、函数调用名。
  - 规则按优先级排序，已着色范围(occupied)跳过重叠，避免注释内关键字被覆盖。
  - 颜色用动态 UIColor { traitCollection } 适配深/浅色（VS Code Dark+ 风格配色）。
  - 直接操作 textStorage（beginEditing/setAttributes/addAttributes/endEditing），不替换 attributedText，光标不跳动；恢复 selectedRange 兜底。
- 集成：
  - makeUIView 设 text 后立即高亮。
  - updateUIView 在 text/font 变化分支后高亮。
  - Coordinator.textViewDidChange 走 debounce 250ms (DispatchWorkItem) 重新高亮，避免逐键卡顿。
- 验证：`swiftc -parse` 通过。
- 经验：UITextView 实时语法高亮应直接改 textStorage 属性而非替换 attributedText(后者会重置选区/光标)；编辑时用 debounce；正则规则需按注释>字符串>关键字>函数名排序并用 occupied 数组跳过重叠。

## 追加：不换行配置未生效 → 强制 TextKit 1 (ScriptPreview.swift)

- 用户反馈上一轮配置后内容仍然换行。
- 根因：iOS 16+ UITextView 默认使用 TextKit 2 布局，`widthTracksTextView = false` 在其中不可靠（长行仍软换行）；且 `textContainer.size = .greatestFiniteMagnitude` 会让 TextKit 内部宽度运算溢出，可能回退为按 textView 宽度换行。
- 修复：`CodeTextView` 改为自定义 `init()`，手动构建经典 TextKit 1 栈（NSTextStorage + NSLayoutManager + NSTextContainer），container 设 `widthTracksTextView = false`、`lineBreakMode = .byClipping`、`size = CGSize(width: 1_000_000, height: 1_000_000)`（有限超大值而非无穷大）；`EditorContainer.setup()` 中移除重复的 container 配置。GutterView/JSSyntaxHighlighter 用的是 TextKit 1 API（layoutManager/textStorage），与手动栈天然兼容。
- 经验：iOS 16+ UITextView 不换行必须用传入自定义 textContainer 的方式强制 TextKit 1；宽度用有限的超大值（如 1e6），不要用 greatestFiniteMagnitude。

## 追加：仍换行 → 定位到 TextKit 2 接管 + enforceNoWrap 双引擎加固 (ScriptPreview.swift)

- 用户第二次反馈仍换行。用 macOS AppKit 探针脚本验证 TextKit 1 布局本身：container 宽 1e6 + widthTracksTextView=false 时 500 字符长行只有 1 个 line fragment（不换行）；宽 320 时 10 个（换行）。→ 证明布局逻辑正确，问题在 UITextView 包装层：iOS 16+ 系统可能无视传入的 TextKit 1 栈，内部静默切到 TextKit 2（textLayoutManager），其自建 container 默认 widthTracks=true → 照旧换行。
- 加固：`CodeTextView` 新增 `enforceNoWrap()`，在 init 和每次 `layoutSubviews` 中对两条链都断言"不换行"配置（widthTracksTextView=false、lineBreakMode=.byClipping、size=1e6×1e6，变化时才 ensureLayout）：
  - `textLayoutManager?.textContainer`（TextKit 2 分支，系统接管时生效）
  - `textContainer`（TextKit 1 分支，防 UIKit 重置）
- 命令行 xcodebuild 仍因系统拦截 SPM sandbox-exec 失败（Xcode 26 环境限制，非代码问题），只能在 Xcode IDE 内构建验证。
- 经验：iOS 16+ UITextView 不换行要"双保险"——手动 TextKit 1 栈 + 每次布局断言 textLayoutManager 容器；判断是否被 TextKit 2 接管可查 `textView.textLayoutManager != nil`。

## 追加：内容被截断 → TextKit 2 容器高度不能撑大 (ScriptPreview.swift)

- 用户反馈 enforceNoWrap 加固后"内容被截断"。
- 根因：上一版 enforceNoWrap 把 TextKit 2 容器的 `size` 整体设为 `1_000_000 × 1_000_000`。TextKit 2 接管布局时，UITextView 的 `contentSize.height` 直接反映现代容器高度 → 滚动区域变成 100 万像素高的虚拟画布，真实文本只占顶部一小条，看起来像内容被截断、滚不到底。
- 修复：`enforceNoWrap()` 只强制**宽度**为 1e6（保证不换行），高度完全保留系统自动值（`CGSize(width: hugeWidth, height: tc.size.height)`），避免 contentSize.height 异常。
- 经验：TextKit 2 下修改 NSTextContainer.size 时，**只能放宽宽度，绝不能动高度**——高度由系统按 usedRect 自动计算；TextKit 1 的容器高度不影响 contentSize（usedRect 决定），可保持 1e6。

## 追加：横向截断（长行右侧看不到）→ 显式 contentSize 兜底 (ScriptPreview.swift)

- 用户反馈：长行的右侧字符看不到、滑不过去（横向截断）。
- 根因：`.byClipping` 的语义是"超宽裁剪而非延展"——容器宽度一旦被系统（TextKit 2）重置回 textView 宽度，长行超出屏幕的部分直接被裁掉；而 UITextView 的 contentSize 并不总是由布局引擎的 usage bounds 驱动，右侧内容既不可见也不可滚。
- 修复：`CodeTextView` 新增 `fixContentSize()`，在每次 layoutSubviews 中：
  - 先对两条链 ensureLayout（幂等增量）：TextKit 1 的 `layoutManager.usedRect(for:)` + TextKit 2 的 `textLayoutManager.usageBounds(for:)`
  - 取两者 used rect 的最大值（含 textContainerInset），直接赋值 `contentSize`（UIScrollView 属性可写），横向滚动范围钉死为最长行宽度。
- 经验：TextKit 双引擎不可控时，终极手段是**自己用 usedRect 计算并显式赋值 contentSize**，不依赖 UITextView 内部推导；`.byClipping` 在容器窄时会静默裁剪长行，务必同时保证容器宽 + contentSize 宽。

## 追加：修复 fixContentSize 的编译错误 (ScriptPreview.swift)

- 用户贴出 3 处编译错误，全部在 fixContentSize 的 TextKit API 用法：
  1. `if let layoutManager` → `UITextView.layoutManager` 是**非可选**属性，不能条件绑定
  2. `ensureLayout(for: glyphRange)` → 当前 SDK 该重载不存在，被解析成 `ensureLayout(for: NSTextContainer)` 报类型错误；正确写法是 `ensureLayout(for: textContainer)`
  3. `tlm.usageBounds(for:)` → 当前 SDK 的 NSTextLayoutManager 没有该成员
- 修复：删掉 TextKit 2 分支，只保留 TextKit 1 链（init 手动构建的栈是 textView 的主布局源、`layoutManager` 始终非可选存在）：`layoutManager.ensureLayout(for: textContainer)` + `usedRect(for:)` 计算 contentSize。
- 验证：`swiftc -parse` 通过；另写 typecheck 探针（UIKit 下 `layoutManager` 非可选 + `ensureLayout(for: NSTextContainer)` + `usedRect(for:)`）对 iphonesimulator SDK 编译通过。
- 经验：修 UIKit API 报错后，最好写个最小 typecheck 探针对模拟器 SDK 验证 API 签名，比只 `swiftc -parse` 更可靠；`NSTextLayoutManager.usageBounds(for:)` 在当前 Xcode 26/iOS 26.2 SDK 中不存在，规避之。

## 追加：横向滚动文字断断续续 → 容器改为"紧贴实际宽度" (ScriptPreview.swift)

- 用户反馈：横向滚动时文字显示断断续续（一段段蹦出来）。
- 根因：容器宽度被强制 1e6 + TextKit 1 的 line fragment 宽 = 容器宽 → `usedRect.width` 虚高成 1e6 → `contentSize` 是百万像素超大画布。UIKit 对超大绘制区域走 CATiledLayer 分块**异步渲染**，横向滚到远处时区块来不及绘制 → 文字断断续续。
- 修复：把 `enforceNoWrap()` + `fixContentSize()` 合并重构为 `synchronizeLayout()`，宽度从"无限"改为**刚好够**：
  - 新增 `widestLineExtent()`：用 `enumerateLineFragments` 枚举每行 `usedRect.maxX`，取文本**实际最长行右端**（不能直接 `usedRect.width`，它 = 容器宽会自我膨胀）。
  - 容器宽 = max(可视宽, 最长行实际宽) + 60pt 余量；两条链（TextKit 1 `textContainer` / TextKit 2 `textLayoutManager.textContainer`）都收敛到该宽度，仅在变化时 ensureLayout。
  - 高度保持系统自动；`contentSize` 仍由 usedRect 显式赋值。
  - 新增 `refreshLayoutAfterTextChange()`，在 `Coordinator.textViewDidChange` 中调用：编辑出更长的行时主动重算容器宽（UITextView 对 contentSize 变化不总跑 layoutSubviews）。
- 验证：`swiftc -parse` 通过；typecheck 探针验证 `enumerateLineFragments(forGlyphRange:using:)` 签名（usedRect 闭包参数为 CGRect）通过。
- 经验：TextKit 不换行编辑器**不要用超大固定容器宽**——渲染区域过大会触发分块异步渲染导致滚动断片；正确做法是按最长行实际宽度收敛容器（enumerateLineFragments 的 usedRect 才是真实字形宽度）。
- 追加：用户报 `ScriptPreview.swift:211` 编译错误——`widestLineExtent()` 里又写了 `ensureLayout(for: glyphRange)`，当前 SDK 无该重载（`for:` 参数是 NSTextContainer）。已改为 `ensureLayout(for: textContainer)` + 注释提醒。**经验补强：凡是 `NSLayoutManager.ensureLayout`，一律传 `textContainer`，不要传 NSRange。**

## 追加：横向滚动黑屏/黑边覆盖 → 宽度安全上限 4096 (ScriptPreview.swift)

- 用户反馈：刚开始滚动黑屏 → 滚一部分显示代码 → 继续滚被右边黑边慢慢覆盖。
- 根因：UITextView 文本渲染（TextKit 1 的 CATiledLayer / TextKit 2 均如此）在**内容宽度超过约 4096pt** 时崩坏——tile 异步栅格化跟不上横向滚动，出现黑屏、黑边覆盖。上一轮"紧贴实际宽度"方案在最长行 <4096pt 时有效，但超长行（约 600+ 等宽字符）会触发。
- 修复：`synchronizeLayout()` 加 `maxContentWidth = 4096`：
  - 容器宽 = `min(max(可视宽, 最长行宽), 4096) + insets + 60`
  - 最长行 >4096 时 lineBreakMode 切为 `.byCharWrapping`（超限行在右缘按字符折行，内容可见），否则保持 `.byClipping`（正常行不换行横向滚动）
  - contentSize 逻辑不变（实际 usedRect 赋值）
- 验证：`swiftc -parse` 通过。
- 经验：**UITextView 不换行编辑器的宽度硬上限是 ~4096pt**，超过必黑块；超限行只能折行，两害相权取"可见的折行"而非"不可见的裁剪/黑屏"。正常脚本行（几百字符）无感。
